# Code Agent Guidelines for the GeoSlicer Project

This document provides strict guidelines for reviewing the GeoSlicer codebase. When analyzing code or generating suggestions, you must adhere to these conventions.

## 1. Core Project Context

- **Project:** GeoSlicer (Digital rock visualization/processing).
- **Base Platform:** [3D Slicer](https://www.slicer.org/).
- **Language:** Python 3.12.
- **Formatter:** Code must adhere to [ruff](https://github.com/astral-sh/ruff) formatting.
- **Dependency Management:** Use `uv` (recommended) via `./setup_dev.sh` (Linux/macOS) or `./setup_dev.ps1` (Windows). `pip` is an alternative.
- **License Compliance:**
    - Verify that new dependencies added to `pyproject.toml` or source files are consistent with the `pylic` configuration list defined in `pyproject.toml`.
    - Flag any dependency that falls under `unauthorized_licenses`.
- **Static Analysis:** The project uses `pre-commit hooks` for static analysis. Check `.pre-commit-config.yaml` to understand which tools are used.

## 2. Module Structure & Path Conventions

When reviewing new modules or refactoring, ensure the following structure and path usage are respected:

- **Directory Structure:**
    - **Module Script:** `src/modules/SomeModule/SomeModule.py`
    - **Integration Test:** `src/modules/SomeModule/Test/SomeModuleTest.py`
    - **Unit Test:** `tests/unit/modules/test_some_module.py`
    - **Test Resources:** `src/modules/SomeModule/Test/Resources/`
- **Path Manipulation:**
    - **Rule:** Use the `pathlib` library for all path manipulations.
    - **Flag:** Flag usages of `os.path.join` or raw string concatenation for paths.

## 3. Testing Guidelines

The project uses two distinct testing methodologies. Ensure code submissions include the appropriate tests and follow these specific implementation patterns.

### 3.1. Integration Tests (Slicer Environment)
These tests run inside the live application.
- **File Location:** `src/modules/SomeModule/Test/SomeModuleTest.py`
- **Inheritance:** Class must inherit from `commons.slicer.tests.ltrace_plugin_test.LTracePluginTest`.
- **Setup/Teardown:**
    - Use `pre_setup()`, `post_setup()`, and `tear_down()`.
    - **CRITICAL:** Do **not** call `super()` when overriding these specific methods.
- **UI Interaction:**
    - Validate that UI widgets are accessed via `self.widgets['objectName']`.
    - **Concurrency:** Ensure `commons.slicer.tests.utils.process_events()` or `wait()` is called after UI actions (like clicks) to allow the event loop to process.
- **Import Pattern:** The main module script (`SomeModule.py`) must handle the absence of tests in production builds using this exact pattern:
    ```python
    try:
        from Test.SomeModuleTest import SomeModuleTest
    except ImportError:
        SomeModuleTest = None
    ```

### 3.2. Unit Tests (Pytest Environment)
These tests run headlessly and must not depend on a running Slicer instance.
- **File Location:** `tests/unit/`
- **Mocking:**
    - `slicer`, `vtk`, and `qt` are mocked automatically by `tests/unit/conftest.py`.
    - Do not suggest adding manual mocks for these libraries within the test files.

## 4. Slicer API Usage & Dependencies

- **Restricted Imports:**
    - **Rule:** Do not import `slicer`, `vtk`, or `qt` in code located outside of `src/modules` or `src/commons/slicer`.
    - **Flag:** Flag any "core" logic or utility scripts outside these folders that attempt to import Slicer-specific libraries.

## 5. Qt Framework Specifics (PythonQt) — CRITICAL

The GeoSlicer environment uses **PythonQt** bindings, not PySide or PyQt. You must adjust your review logic to prevent hallucinations based on standard Qt Python libraries.

- **Forbidden Libraries:**
    - **Flag:** Any import from `PySide2`, `PyQt5`, or `PyQt6` (e.g., `from PySide2.QtWidgets import QWidget`).
- **Correct Library:**
    - **Accept:** Imports using the `qt` module (e.g., `import qt`, `qt.QWidget`, `qt.QPushButton`). This is the correct binding for 3D Slicer.
- **Syntax Differences:**
    - **Property Access:** PythonQt often exposes getters/setters as Python properties.
    - **Rule:** Do not "correct" syntax like `pushButton.text` to `pushButton.text()`. Both may work, but property access is preferred and valid in PythonQt.
    - **Review Strategy:** If the code looks like valid PythonQt but invalid PySide2, assume it is correct.

## 6. Code Style & Naming

Enforce naming conventions based on the specific library being interfaced with:

- **CamelCase (`myVariableName`, `calculateVolume()`):**
    - **Mandatory for:** Scripting within GeoSlicer modules that interact directly with Qt, 3D Slicer, and CTK classes.
- **Snake_case (`my_variable_name`, `calculate_volume()`):**
    - **Mandatory for:** Internal logic, LTrace library code, and any code that does not directly interface with Qt/Slicer APIs.
- **PascalCase (`MyClassName`):**
    - **Mandatory for:** Class names and Module file names.
- **Line Length:** 120 characters (PEP 8 exception).
